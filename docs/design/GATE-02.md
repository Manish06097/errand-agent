# Gate 2: memory and context design

Status: signed off on 2026-11-09, all four questions taken as recommended. Main is at 777ffc4 (M0 to M4, M10, M15). Of this gate's scope only the memory tables (migration 0001) and the M3 builder (S1, S2, S3, S6, S7) exist; M11 and M12 build the rest.
Detail lives in `architecture.md` (section numbers in brackets) and ADRs 0006 and 0007. A bracket means the design already decided it. **New** marks a call the design was silent on, **amends** a change to a written section. A second review checked this against the brief, the design and the code on main; it corrected the budget figures and added the in-flight forget, memory-as-data and canary-placement rules.

## Decisions

### Memory registry

1. **One typed row per fact, in the table that already exists** [12.1] - `memory_id`, `user_id`, `key`, `scope` (`global` or `service:<name>`), `value_json`, `value_hash`, `kind` (`explicit`, `inferred`), `status` (`active`, `pending_confirmation`, `superseded`, `forgotten`, `rejected`), `evidence_json`, `supersedes` and `superseded_by`, and `created_at`, `confirmed_at`, `forgotten_at`, `last_used_at` in epoch ms on the agent clock. One active row per (user, key, scope). The builder reads only `memories_eligible` (status `active`) - rejected: a vector store, free-text notes.
2. **The registry is code, one entry per key** (**new** in this form; 12.1 lists the keys but not their rules). Unknown keys and badly typed values are tool errors.

   | key | value | scopes | pinned | feeds | errand kinds | inferred by |
   |---|---|---|---|---|---|---|
   | `home_area` | Area enum | global | yes | brief `area` | book, rebook | - |
   | `earliest_time`, `latest_time` | time | global, service | yes | window `not_before` / `not_after` | book, reschedule, rebook | `latest_time` 12:00: 3 of the last 4 bookings before noon |
   | `avoid_days` | weekdays | global, service | no | window | book, reschedule, rebook | - |
   | `budget_ceiling` | INR | service | no | brief `budget_max_inr` | book, rebook | - |
   | `preferred_provider` | provider id | service | no | ranking `pref_match` (pins only on "same as last time", 7.3) | book, rebook | same provider twice for a service |
   | `avoid_provider` | provider ids | service | no | hard filter (10.2) | book, rebook | - |
   | `language` | enum | global | no | reply language | all | - |
   | `access_note` | text, 120 chars, cleaned like world text | global | no | context only, never code | book, rebook | - |
   | `contact_window` | time window | global | no | follow-up notify policy (gate 3) | follow-up | - |

   Evidence is `{user_msg, message_id, start, end, quote, cue}`, `{ui_action, client_action_id}` or `{rule, booking_ids}`. Contradicting pairs: preferring and avoiding the same provider in one scope (the newer write supersedes the older in one transaction, and the dialog or chip says what it replaces), and an `earliest_time` at or after its scope's `latest_time` (refused).
3. **Explicit means you stated a standing preference, and code checks it** [10.7, 12.2] - `remember(key, scope, value, evidence)` needs a span of the current user message that contains the value and a standing-preference cue (always, never, from now on, every time, I live in, I prefer, my usual). **New:** key-specific cues ("I moved to", "I've moved to" for `home_area`, so S32's correction counts), and a one-off marker in the same span ("this time", "today", "for now", "just for") vetoes the cue, so "this time I prefer after 5" saves nothing. The cue table is a unit-tested pure function. Without a cue the write becomes a brief patch plus a "Remember this for next time?" chip, and a click on it is the cue (`ui_action` evidence). An add or edit on `/memory` is explicit too. The row is `active` at once, with a "Saved" chip and Undo - rejected: letting the model classify.
4. **Inferred means a code rule over your booking records guessed it, and it stays pending until you click Keep** (**amends 12.2, 10.3 and ADR 0006**, which also let the model write `remember(claim="inferred")`) - the only source is `memory/inference.py` after each completed errand, with the two rules in the table. `remember` loses its `claim` argument: a model guess goes through the "Remember this?" chip and becomes explicit on your click, so the user experience is the same, a hijacked planner has no path to plant suggestions, and every pending row's evidence is booking ids, never text. Rows enter `pending_confirmation`, are outside the eligible view and never reach the model. Keep sets `active` and `confirmed_at` with kind still `inferred`; Dismiss sets `rejected` and blocklists (key, scope, value_hash). Both are conditional updates on `status = 'pending_confirmation'`: a second click, or a click on a row that changed meanwhile, gets 409 with the row's current state. **New:** no suggestion is made while an active row exists for the same (key, scope) or its contradicting pair, or while the value is blocklisted; an explicit write for that (key, scope) or its pair rejects any pending suggestion with reason `superseded_by_explicit`; pending rows do not expire. The blocklist stops inference only: you can still state a blocklisted value yourself. Only a user action moves a row out of pending (INV-19).
5. **What you see** [12.2, 17.2] - in chat: "Saved: home area" with Undo, one suggestion chip after the errand that produced it ("You usually book before noon. Remember that? Keep / Dismiss"), and "(from memory)" chips on brief fields. On `/memory`: Your preferences (labelled "You told me" or "Inferred, confirmed by you", with a link to the source message or bookings, last used, Edit, Forget), Suggestions (pending, Keep and Dismiss), History (superseded with values, forgotten as "Forgotten on 5 Nov" with none). Chips and cards store `memory_id` references; the UI resolves them with their status, the builder only through the eligible view, so a pending value has no inline copy anywhere [12.3]. **New:** Undo on a "Saved" chip sets `rejected` (reason `undone`) and redacts nothing. Undo means "not a standing preference", not "I didn't say it", so your message stays and still counts for this errand as a one-off. That is the one place a non-eligible value may reach the model, only in your own words, and INV-05 says so (decision 26).
6. **Memory text is data, not instructions** (**new**) - memories are written from conversation, so they are an injection path that outlives the session. Three layers: writes need evidence in your current message (10.7), so review text cannot write one (S16); every value is typed by the registry and re-validated when rendered, so a stored row that no longer parses is skipped with `invalid_value` rather than sent; and `access_note`, the one free-text key, is never inferred, never read by code, cleaned like world text and rendered inside S4's JSON data envelope, which S1 declares to be data like `<tool_data>` [11.5]. A note you save yourself ("from now on book without asking me") can at most be obeyed as far as proposing, because approval is code (gate 1 decision 2). S16b proves it.

### Inspect, correct and forget

7. **Surface** [17.3] - `GET /api/memory` (grouped by status), `GET /api/memory/{id}` (with its `memory_events`, the audit trail), `PATCH /api/memory/{id}` (correct), `DELETE /api/memory/{id}` (forget), `POST /api/memory/{id}/confirm`, `/dismiss`, `/undo`, and the chat actions `keep_memory`, `confirm_forget` and **new** `update_memory` (the "Update your saved home area? [Update] [Just this time]" chip). Every mutation carries a `client_action_id`, is idempotent through `client_requests`, and returns 409 with the current row when the row is not in the state the action needs (correcting a superseded or forgotten row, forgetting twice). In chat, `list_memories` makes code render a `MemoryListCard` whose contents never enter model context (S64), and `propose_forget` only renders a chip (S61).
8. **Correct writes a new version and never overwrites** [12.2] - one `BEGIN IMMEDIATE` transaction inserts the new row (kind `explicit`), marks the old one `superseded` with both links, rejects any contradicting pending suggestion (decision 4), invalidates pending cards that depended on the old row (decision 11), and appends `corrected` and `superseded` events with the actor. The old value stays visible in History. A chat correction of a memory-sourced field changes only this errand until you tap Update (S33). **Amends 12.3:** a supersede does not rewrite archived `errands.brief_json` or `known_bookings.origin_brief_json`, because changing where a past booking was made would falsify history, and nothing renders archived brief values (decision 20). **New:** the old row's evidence span gets a model-view redaction ("[updated preference]"): your transcript still shows what you wrote, but only current preferences reach the model even inside the last six turns, and INV-05 holds for superseded canaries without a carve-out.
9. **Forget is your click and it is final in `agent.sqlite`** [12.3] - one transaction: status `forgotten`, `forgotten_at`, blocklist row, `message_redactions` from the evidence offsets and every surface form of the value, every brief field with that `prov.memory_id` cleared in archived errands and `origin_brief_json` with its evidence quote, `invalidate` records, dependent pending cards invalidated (decision 11), then `value_json` set to NULL. **New:**
   - The redacted spans are overwritten in `messages.body_json` in the same transaction, not only overlaid, so after a forget `agent.sqlite` holds no plaintext copy of the value. As 12.3 was written the overlay left the text in place, and the dialog's "cannot be recovered" would have been false. What stays on disk elsewhere is question 2.
   - Forgetting a key forgets its superseded ancestors too, each with its own events; the dialog says "and 2 earlier values". That is what "forget my home area" means.
   - The 8-second undo lives in the browser, which waits and then sends DELETE; the server forgets at once. If the page is closed inside the window, the browser sends the DELETE right away (`fetch` with `keepalive` on `pagehide`), so a click is never silently lost. 12.3 step 6 had a short-lived server event, which is one more half-applied state a crash can leave.
   - The surface-form hashes, and a hash of each redacted span's normalised text, go in a new table (migration 0004), HMAC-keyed with a per-install secret kept outside `agent.sqlite`. They drive the mask (decision 13) and the trace reader (decision 14) without plaintext. They stop re-display, not someone holding both files, and the README says so.
10. **Amends 12.3: the open errand cannot share that transaction** - the open errand's brief lives in `checkpoints.sqlite` (`ThreadState.errand`), a different file, and so do the open errands of your other conversations. So:
    - the builder treats any brief field whose `prov.memory_id` is not in `memories_eligible` as missing and never renders it, which holds even while a checkpoint is stale;
    - `ingress` clears those fields at the start of each thread's next run, or re-fills them from the active successor after a correct, and writes the result into the next checkpoint (idempotent, so a crash just repeats it);
    - every write of a brief into `agent.sqlite` (archiving an errand, `origin_brief_json` at verify, an approval's material) goes through the same scrub, so a stale checkpoint can never write a forgotten value back;
    - the conversation state API applies the same filter, so the State panel never shows the value either.
11. **A forget or correct that lands while something depends on the row** (**new**) - memories are per user, so this can come from another tab mid-run.
    - **A run in flight.** Every memory mutation bumps a per-user `memory_epoch` (migration 0004). The builder records the epoch it read in the manifest; before each loop call the gateway compares it, and on a change rebuilds the request from state with the new eligible set before sending. A call already sent finishes; nothing sent after the forget commits carries the value. M11 builds this rebuild step and M12's compaction reuses it.
    - **A pending card.** `approvals` gains `memory_ids_json` (migration 0004): the memory ids behind the brief fields at proposal time. The forget or correct transaction invalidates every `pending` approval that lists the row with `request_changed`, when M8's `INVALIDATES` table says a change to that field invalidates the card; the card updates over SSE and a click on it gets the usual 409 (8.5). `prepare_proposal` checks in its own transaction that every id it lists is still eligible, so a card cannot be created from a row forgotten a moment earlier.
    - **A granted approval or an open intent** is left alone: you approved the provider, slot and price, none of which is a memory value, and stopping a booking halfway is worse than finishing it. The booking completes and its `origin_brief_json` is scrubbed (decision 10).
    - **A pending suggestion** for the same key is rejected by a correct (decision 4).
12. **Forget vs booking history: bookings stay** [12.3 nuance, question 1] - a booking is a fact of the world. Forgetting "preferred electrician: E4" removes the row, your statements of it and every brief field sourced from it. World bookings, `known_bookings` rows, `list_bookings` results and ledger lines stay, so "same electrician as last time" still finds E4 from history.
13. **Amends 12.3 steps 3 and 5: redaction and the n-gram mask cover what people and the model wrote before the forget, not records** - as written, the mask scans S3, S5, S6, S7 and compacted tool results, which would mask every 10:00 slot after forgetting "not before 10" and every Arjun booking line after forgetting a preferred provider. Both now cover user and model text in messages created before `forgotten_at` (including the model-written parts of cards: a ClarifyCard question, a shortlist recommendation) and brief evidence quotes from those messages. They skip S7, which is you speaking now and may restate the fact on purpose, code-rendered material (slots, prices, provider names, booking lines, the ledger) and world tool results. Over-masking inside that scope is accepted: an old "Indiranagar" about something else is masked too.
14. **Forget vs traces and checkpoints on disk: mask on read, never rewrite** (**new**, question 2) - the JSONL trace is the append-only record of what was sent, and `model.call` holds the sanitized request, so a past request can hold a value forgotten later. Every user-facing read path goes through `trace/reader.py`, which applies the hashed spans and the mask before anything leaves the process: the trace panel, `/runs/[id]`, SSE replay, `errand-trace show` and `export`. The evals read the raw files on purpose: INV-05 and INV-20 must see a leak, not a masked one, and a test checks both routes. `memory.*` records already carry hashes only [16.2]. Older checkpoints of a thread keep the old brief; nothing reads them (no time travel, and recovery reads our tables, gate 1 decision 7). The README states that the trace files, older checkpoints and Langfuse, when on, keep a forgotten value until deleted, and corrects the forget-vs-traces row in section 21, which claims a sanitizing the trace does not do.

### Relevance scoring and selection

15. **Relevance is a gate, the score only orders** (**amends 13.2**) - a row is a candidate only if it is eligible, its scope is global or the brief's service (else `irrelevant:scope`), and the registry says its key applies to the errand kind (else `irrelevant:kind`). As 13.2 was written, applicability was a weighted term under a 1.0 threshold, and `1·[explicit]` alone clears 1.0, so every explicit global row went into every request: `contact_window`, which only feeds follow-ups, would ride along on every booking. Candidates are ordered by 13.2's score without the now-constant applicability term: `3·[scope matches service] + 2·[pinned] + 1·[explicit] + 0.5·recency_decay(last_used_or_created, half-life 60 d)`, and packed greedily into S4.
16. **Conflicts, ties and staleness** (**new**) - a service-scoped row shadows the global row of the same key (`shadowed:scope`), so an electrician `earliest_time` of 10:00 beats a global 08:00. Ties go to pinned first, then registry order, then service scope before global, then `memory_id`. No expiry: an old preference stays until you change it, and age only lowers its rank. `last_used_at` moves once per run, at `run.end`, for active rows that were in a sent request, so scores never shift between calls inside a loop. S4 renders the chosen rows in registry order, so the bytes change only when the set does.
17. **Pre-fill** [13.2] - a required brief field with a matching candidate is filled by code with `prov.source="memory"` and `prov.memory_id`, shown as "(from memory)". **Amends 13.2:** global keys are filled in `ingress` at errand start, and service-scoped keys inside `update_brief`'s merge when the service is set or changed, because `ingress` runs before the model has set the service and a plumbing budget ceiling would arrive a turn late. A field you clear is not refilled in that errand, and the current message beats memory [12.2]. Pre-fill lands in M11, since S49 needs it; scoring lands in M12.

### Context budget

18. **12,000 estimated input tokens per request, hard** [13.1, ADR 0007] - `LLMGateway` never sends over the cap. The estimate is `ceil(utf8_bytes / 1.5) + 8` per block plus 400 for the tools preamble, over every block including replayed thinking and tool_use; inside the loop the gateway takes the larger of that and the previous call's reported input plus output plus what was appended. A live test checks it never undercounts `count_tokens` on thinking-bearing fixtures, and in replay and live modes INV-06 also checks the reported input tokens.
19. **A new split** (**amends 13.1**, question 3). Measured on the eval traces at 262c12b: S1 1,402; S2 1,996 for 6 of the 11 tools, with the 400-token preamble outside it; S3 at most 899 (S55); S6 at most 606 (S62); S7 at most 97; 113 more for message and block framing that no section counts; the largest request 7,933 (S12). Inside the loop, the last call of a run is about 3,070 above its first in ordinary booking flows (S06, S31) and 3,760 in the hostile S12. These are scripted planners with no thinking blocks, so live loops are larger; M16's cassettes measure that. Two things break the current table. The preamble sat outside S2, so it really summed to 12,400. And the tool list cannot stay at 2,000: M8's `not_before`/`not_after` on the window take `update_brief` from 984 to about 1,080, which puts the list over its cap in M8, and a sketch of the five tools M9 and M11 add, at today's description length, measures about 1,170, so 11 tools come to about 3,660 with the preamble.

    | Section | Now | Gate 2 | When full |
    |---|---|---|---|
    | S1 rules (cached) | 1,600 | 1,600 | fixed; a test fails over cap |
    | S2 tools, preamble included | 2,000 + 400 | 3,800 | fixed order, stable bytes; a test fails over cap |
    | S3 errand state | 1,100 | 1,100 | sub-caps (13.1), then `CONTEXT_EXHAUSTED` |
    | S4 memories | 700 | 600 | greedy in score order; lowest non-pinned row dropped as `over_budget` |
    | S5 ledger | 400 | 400 | newest first; the rest as "and N earlier errands" |
    | S6 recent turns | 1,800 | 1,000 | whole turns, newest first; oldest turn dropped |
    | S7 current message | 1,000 | 1,000 | must fit; else `CONTEXT_TOO_LARGE`, no call |
    | S8 loop reserve | 3,100 | 2,300 | a floor, not a ceiling |
    | slack (covers the framing) | 300 | 200 | |
    | **Total** | 12,400 | **12,000** | a config test fails if the caps do not sum to the hard cap |

    S8 is the loop room guaranteed when every section is full; the loop may use whatever S1 to S7 leave unused, and the per-call floor check is the only gate. A heavy but realistic request (11 tools, a full S6 and S5, a 30-booking S3, a typical S4) comes to about 7,900 on its first call, so an ordinary 3,070 loop still fits with room; compaction starts only when S3, S6 and S7 are all near their caps at once. S4 rarely binds: after shadowing there is at most one row per key. A test renders every registry key at its longest value and it must fit in 600 (my sketch puts it near 490), and S42c lowers the cap by config to exercise the drop rule.
20. **What gives way first** - no model ever summarises [13.3, 11]. At build time each section sheds by its own rule above and never borrows from another or from slack. Older history enters only as ledger lines built by code from archived errands and `known_bookings` ("2 Oct: booked Arjun Electricals Sat 11:00, ₹600, completed"), with booking-record fields only and never a brief value. Inside the loop, when the floor would cross the cap, the loop compacts once [13.1]: a fresh request from state, thinking and tool_use blocks dropped, this run's tool results as text at their per-tool caps. **New:** if that still does not fit, it sheds S6 down to the latest turn, then S5, then S4 down to pinned rows. S1, S2, S3 and S7 are never shed. Only then `CONTEXT_EXHAUSTED`. Hard filters such as `avoid_provider` are applied by code, so shedding S4 costs the model an explanation, never a constraint.
21. **The logged manifest** [13.4] - one `context.built` per model call, the gateway's figures merged with the builder's, ids and reasons only, never values. M12 adds `memory_epoch`; `memory_included` (`id`, `score`, `prefill`); `memory_excluded` with a reason for every one of your rows, from the closed set `forgotten`, `pending_confirmation`, `superseded`, `rejected`, `irrelevant:scope`, `irrelevant:kind`, `shadowed:scope`, `over_budget`, `invalid_value`; and `ledger_lines`, `turns_dropped`, `masked`, `compacted`, `shed`. The trace panel's Context view renders it, and INV-20 checks it against the request it describes.

### Seed data

22. **Two seeds** (**new**) - `memory_demo`: eight realistic rows, no canaries, for `make dev`, the recorded demo and the memory variants of S01 and S08. `memory_rich_v1`: the 60-row canary seed of 13.5, for evals and as a dev drawer scenario. Canaries in the demo's Suggestions list would look broken.
23. **What `memory_rich_v1` holds and where its canaries go** (**amends 13.5**, whose mix had no confirmed inferred rows and whose canaries assumed every row has text) - 20 active explicit, 4 active inferred and confirmed, 8 active but irrelevant (pest control and painting scopes, keys that do not apply to a booking), 8 superseded (one three-version `home_area` chain), 7 forgotten, 9 inferred pending, 4 rejected (2 dismissed, 1 undone, 1 `superseded_by_explicit`). Conflicts on purpose: the `home_area` chain; a global and an electrician `earliest_time`; an explicit plumber `avoid_provider` P7 with two past P7 bookings, so the rule must not suggest P7; a pending inference rejected by a later explicit write. Also 240 messages over 6 sessions in the demo thread, 6 archived errands, 30 upcoming bookings for S3's sub-caps, and the E4 and A2 bookings [13.5]. Canaries go only where text exists:
    - forgotten rows: a unique canary (`CANARY-FORGOTTEN-7731`) in the evidence quote, other user messages, assistant messages, card bodies, archived brief evidence and `origin_brief_json`, and some of these sit **inside the last six turns** of the demo thread, so redaction and the mask do real work in S6 rather than passing because old messages never reach context;
    - superseded rows: in the evidence span, also partly inside the S6 window;
    - `access_note` rows, the one text value, in each non-eligible status that key can have;
    - the undone row: in your own message, which the seed manifest marks `user_words_kept` (decision 5).

    Pending and dismissed rows are rule-inferred with typed values and booking-id evidence, so they carry no text a canary could sit in. For those the proof is structural: INV-20 checks that no non-eligible `memory_id` is rendered in S3 or S4, and INV-05 checks that no pending or dismissed (key, value) pair from the seed manifest appears in S3's brief or in S4.
24. **Generated deterministically, through the real code paths** (**new**) - `errand.seed` builds it from fixed phrase tables with the keyed RNG (ADR 0010), stepping the SimClock from a fixed epoch, with fixed ids (`m-01` to `m-60`, `msg_0001` on). Every write goes through the memory service, the message repo and the real forget path: each explicit row comes from a seeded user message carrying its cue, through the same evidence check, and each inferred row from the rules over seeded bookings, so redactions, blocklist rows and surface hashes are exactly what production makes; nothing is inserted as raw SQL. It writes a manifest (`backend/evals/fixtures/memory_rich_v1.json`: each row's id, key, scope, kind, status, canary and where it was planted). A test builds it twice and compares the dumps byte for byte, and checks each canary is unique and planted where the manifest says. Expected context sets are written by hand in the scenario YAML, never derived from the scorer.

26. **Invariants** - INV-05 and INV-06 [18.5] run on every scenario from M11 and M12. Two new ones:

Guards S15, S16, S60 and S61.

It reads the raw request, so the manifest cannot vouch for itself.

## Questions for you

1. **Forget vs booking history (12.3): bookings stay?** *My recommendation: yes, as in decision 12.* Masking booking records would make forget feel more complete, but it breaks "same electrician as last time" for a record that is the provider's, not a preference of yours.
2. **Forgotten values outside `agent.sqlite`: mask on every read, or rewrite traces and prune checkpoints?** After decision 9 the app's own database keeps no plaintext of a forgotten value. The JSONL traces, older checkpoints and Langfuse (when on) still do. *My recommendation: mask on read (decision 14) and say so in the README.* Rewriting would break the request hashes and the append-only trace the evals read, and editing checkpoints of a thread parked at an interrupt is fragile. The cost is that someone reading the raw files under `data/` can still find the value.
3. **S2 to 3,800 tokens (preamble included), paid for by S6 (1,800 to 1,000), S8 (3,100 to 2,300), S4 (700 to 600) and slack (300 to 200)?** *My recommendation: yes, applied in M8, the first milestone past 2,000.* 11 tools project to about 3,660, so this leaves about 140 of headroom. The alternatives are squeezing 11 schemas into 2,000 (`update_brief` alone is 984), which gives the model worse descriptions, or raising the 12,000 cap from gate 1, which I would rather not move.
4. **Gate 1 Q1, the same-key retry after an ambiguous `book` timeout and a `not_found`: confirm or flip before M5.** GATE-01 records it as taken, but the sign-off on it was a bare "ok" to a changed recommendation, which is thin for the one rule M5 is built around. *My recommendation: confirm.* The brief makes status authoritative and gives `book` a key so the provider dedupes; flipping means the wait rule for about 7.5% of bookings (up to 10 minutes and a second click). Either way it is one config value (`booking.max_same_key_retries: 0` flips it), and both paths get built and tested in M5 and M6 (S23, S68 to S70).

## Decisions taken

1. Bookings stay when a memory is forgotten (decision 12). Forget clears the preference, not the provider's record of a booking.
2. Forgotten values outside `agent.sqlite` are masked on every read (decision 14): traces, older checkpoints and the Langfuse export are not rewritten. The README says plainly that the raw files under `data/` can still hold the value.
3. S2 goes to 3,800 tokens (preamble included), paid for by S6 1,000, S8 2,300, S4 600 and slack 200, applied in M8.
4. Gate 1 Q1 is confirmed: after an ambiguous `book` timeout and a `not_found`, one retry with the same idempotency key on the still-valid hold, then verify again. `booking.max_same_key_retries` stays at 1; 0 is the documented alternative.
